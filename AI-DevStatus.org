* Key Design Decisions
- Session-Root, native and foreign (2026-11-02; bisos.aiActivity's ModelAndTerminology panel): a
  window's folder is its sessions' Session-Root and must be an AI-Activity Root; a buffer's window is
  opened on its home; a window is focused by true name and never replaced; conflicts between sessions
  are warned, not refused. Working across several AI-Activities in one session is normal.
- Layers: a lower layer never names an upper one (Stage 13); layer 0 states a contract (=register==,
  =walk==, gitOpener) instead of naming Blee code. Python first; one CSXU per elisp layer.
- The Emacs layer is optional and does not interfere: Claude reaches Emacs only when a prompt names it
  (=emacs=<socket>=) or the user asks; hookToEmacs does nothing without a live partner.
- One Emacs partners with one VS Code; =b:vscode/init= is run by hand, not at startup (a second, test
  Blee must not take the partner role).
- You press Enter, unless asked (x x, C-u, the =S== links).
- The driver (2026-11-23, 7.3/7.4): actions in E, V, P, S order on every row, within 105 displayed
  characters; P links where you may type (a P =ai-outputs= with the defect after it is a capture, so no
  separate capture link); S only where nothing is typed (git-commit-walk, git-pull-list-add); Close in
  the order of a session's end --- session-verify and skills-improve first (they change files), then
  the walk, then the pull list (it needs pushed commits). =initiate= stays out: the driver lives in a
  WorkPlan, which exists only after it. Link prefix =aiActivity:=, not =bx:= (too generic).
- The driver's marks (2026-11-24, 7.4.1): each link carries its kind, so a row may list its links in
  any order. Faces go around the link (=*[[...][$x]]*=), the sigil inside its text. =!= submit is
  underlined (red in Blee's theme): final, nothing to edit, it must stand out; =#= prompt has the
  link's own face. Rows within 105 as Blee shows them (=org-hide-emphasis-markers= t); shown markers
  add 2 per marked link. Rejected: faces inside the link text (org ignores them), verbatim (the link
  is no longer followed), strike-through (not readable), a separate READMEs row.
- Moment-to-moment state is shown, not written: the State line is an overlay (=display= over a fixed
  placeholder), so a Refresh never modifies the WorkPlan or reaches git; per Emacs, per buffer, gone
  on revert or rewrite. Writing it as text was rejected: churn in 41 committed WorkPlans, meaningless
  on another machine, and a modified buffer after every Refresh.
- The newResume row (Mohsen, 2026-11-23, 7.5): named to pair with =newStart=, both rows for the
  machine you have just come to (=Resume=, =Continue=, =ReNew= considered). Its command is
  =newResume-confirm=, not =session-resume=: the new session has nothing to do with the one that
  closed --- only the work continues --- and "session-resume" would say otherwise. Read-only: it
  checks the pull list and recommends; pulling, reinstalling, releasing, rebuilding are the user's.
  The repo of the pull lists is pulled first (=outputs-pull=); the pull list itself is the record
  (its entry marked DONE once pulled).
- No elisp for =code --add= and =code --diff= (10.4, 10.5; Mohsen 2026-10-30): not part of the Blee
  workflow; =vscodeAddFolder= and =vscodeDiff= stay in vscode.cs for the shell. Revisit if a use from
  Blee appears. Likewise no =b:vscode/openUrl= (10.6): Blee reaches VS Code only through vscode.cs.
- Dblock updating from outside Emacs is Blee's, not vscode's: =bx-dblock -p emacsSocket== uses exactly
  the socket given, no fallback (6.2).
- VS Code only: claude-code.el stays Blee's separate terminal-Claude path. No MCP server in this phase
  (channel 3 is emacsclient).
- Menus are built once; nothing on =menu-bar-update-hook= (a rebuild there made Blee slow, 2026-10-31).

Found the hard way:
- Org shows no face for emphasis inside a link's text, and verbatim or code around a link makes it
  literal; a batch-test stub of =bx:dblock:control|wrapper= must call through (its advice is
  =:around=), else the dblock writes nothing (2026-11-24; now in the =blee-pkg-authorship= skill).
- Blee sets =straight-check-for-modifications= to nil: a new =.el= file needs its link in straight's
  build dir (a =straight-rebuild-package=), else Blee's startup stops (13.1).
- A Blee started before Stage 13 kept magit's =x= on the old =b:vscode:claude:magit/dispatch= (no x n);
  a restart, or one =define-key=, fixes it.
- VS Code matches a folder by the spelling it was opened with: =/bxRepos/...= and its true name are two
  folders to it (a plain =code <truename>= opened a second window); =windowFocus= passes the open
  window's own spelling (from its storage.json).
- Bash files that declare =major-mode: shellscript-mode= made every bash dblock update fail silently
  (fixed in =blee:buf:re-major-mode=); =org-dblock-update-file-bx= binds =debug-on-error= to nil when
  called non-interactively, else Blee's debugger holds the client in =*Backtrace*= (6.2).
- An org-mode archive in Blee saves the archive file at once but leaves the WorkPlan buffer modified:
  editing the WorkPlan on disk meanwhile loses one side (2026-11-22; it left 4.1 archived twice). Check
  for unsaved buffers before writing a WorkPlan.
