* Key Design Decisions
- The Emacs layer is optional and does not interfere: Claude reaches Emacs only when a prompt names
  it (=emacs=<socket>=) or the user asks; hookToEmacs does nothing without a live partner.
- Layers: a lower layer never names an upper one (Stage 13); layer 0 states a contract (register=,
  walk=, gitOpener) instead of naming Blee code.
- One Emacs partners with one VS Code; a window's folder is a root dir; sessions hold a hierarchy of
  AI-Activities (root by /bx-confirm-root, more by /bx-confirm-here). Associations: activity dir to
  session, by walk-up; a base-dir need not be a repo.
- Python first; one CSXU per elisp layer.
- You press Enter, unless asked (x x, C-u, the S toggle; after |S| in the driver).
- b:vscode/init is run by hand, not at startup: a second (test) Blee must not take the partner role.
- VS Code only: claude-code.el stays Blee's separate terminal-Claude path. No MCP server in this
  phase (channel 3 is emacsclient); NextSteps.org item 1 suggests revisiting that.
- Dblock updating from outside Emacs belongs to Blee, not to vscode: =bx-dblock -p emacsSocket== (6.2).
- Pointers outside this repo's import chain: NextSteps.org (here, not imported); the design paper
  =Emacs+VS-Code+Claude.org= (superseded by README.org); the /bx-confirm-root command and "Root and
  Here" in aiTemplates-workFlow; the =blee-pkg-authorship= skill in aiTemplates-DE (WorkPlan 2.1,
  2.3); the 6.2 changes in bisos/blee (bin/bx-dblock, bin/bleeLib.sh) and blee/env3
  (legacy/bx-dblock-lib.el).
